# GradPath Phase 4 — Skill Gap Analysis Engine

## 1. Purpose

Phase 4 connects the candidate profile produced by Phase 3 with the
existing GradPath skill vocabulary, job-market evidence, and selected
ESCO occupation-skill relationships.

The engine produces a deterministic, explainable assessment for the
supported target roles:

- Data Analyst
- Data Scientist

It is a baseline analysis engine. It does not generate learning
recommendations, certify proficiency, or calculate job-readiness.

## 2. Inputs and sources

The engine loads these existing processed datasets:

| Input | File | Purpose |
|---|---|---|
| Canonical skill vocabulary | `data/processed/initial_skill_vocabulary.csv` | Stable skill IDs, names, categories, roles, and aliases |
| Market priority evidence | `data/processed/skill_priority_scores.csv` | Observed job counts, frequency, market rank, and evidence labels |
| ESCO occupation-skill data | `data/processed/esco_role_skills_clean.csv` | Selected role-specific essential/optional relationships |
| Candidate profile | Generated by Phase 3 | Extracted skills, evidence, verification statuses, and document metadata |

The engine checks that required source columns exist and rejects duplicate
canonical skill IDs in the vocabulary.

Only the two supported target roles are accepted.

## 3. Candidate skill statuses

Each applicable canonical vocabulary skill receives a candidate status.

| Status | Meaning |
|---|---|
| `verified_skill_present` | The input profile explicitly marks the skill as verified. The engine preserves that status; it does not independently validate proficiency. |
| `mentioned_unverified` | The skill was extracted from the CV but remains unverified. A mention alone is not proof of proficiency. |
| `rejected_evidence` | The profile marks the skill evidence as rejected; it is not counted as demonstrated. |
| `potential_gap` | The skill was not detected in a profile whose extraction is not flagged as incomplete. This is a lead to investigate, not proof that the candidate lacks the skill. |
| `insufficient_evidence` | The skill was not detected and the profile has missing/invalid text metadata, a failure-like extraction status, or extraction warnings. |

A missing skill mention is never treated as a confirmed lack of proficiency.

The engine conservatively treats a profile as having incomplete extraction
when its extraction status is one of `failed`, `error`, `empty`, `no_text`,
or `unsupported`, its text character count is missing/invalid/less than one,
or it has extraction warnings.

## 4. Market evidence and priority score

The engine carries forward these fields from the Phase 2 market-priority
dataset:

- `market_jobs_with_skill`
- `market_relevant_jobs_total`
- `market_observed_frequency_pct`
- `market_priority_rank`
- `market_evidence_level`

The Phase 2 observed frequency represents the percentage of relevant jobs
in the current dataset that matched the skill under the existing detector.
It is not a universal estimate of employer demand.

### Priority score

The current score is:

`priority_score = round(min(max(observed_frequency_pct, 0), 100), 2)`

This is a capped, market-only descriptive score on a 0–100 scale.
It is not a probability, candidate readiness percentage, proficiency score,
or measure of total skill importance.

ESCO importance does not add points to this score. The ESCO relationship
and market priority are reported separately so that occupation-framework
evidence cannot silently override the observed market ranking.

Results are sorted by:
1. Descending market-only priority score.
2. Ascending Phase 2 market priority rank when scores tie.
3. Canonical skill ID as a deterministic final tie-break.

### Market evidence status

The engine labels observed evidence using the number of jobs with a match:

| Jobs with a detected match | Engine status |
|---:|---|
| 0 | `no_observed_matches` |
| 1–5 | `limited_observed_evidence` |
| 6–10 | `moderate_observed_evidence` |
| 11 or more | `stronger_observed_evidence` |

These thresholds describe the size of the observed evidence, not its
statistical certainty. Zero detected matches do not prove zero demand.
Job descriptions may be incomplete or truncated, and the detector may miss
skills that are expressed using unrecognized wording.

## 5. ESCO mapping policy

The initial engine deliberately uses a small explicit mapping rather than
fuzzy matching or guessed equivalences:

- `Statistics` maps to the ESCO label `Statistics`.
- `Data Engineering` maps to the ESCO label `Data Engineering`.

A mapping is applied only when the exact canonical ESCO label is present
for the selected GradPath role. If a mapping is not available or the label
is not found, the engine reports `not_mapped` and relationship `none`.

This is a coverage limitation, not evidence that ESCO has no related
concept for the skill. Future mappings should be reviewed and documented
rather than silently inferred.

The engine reports `essential`, `optional`, or `none` separately from
market frequency and priority score.

## 6. Output fields

Each result contains:

- Role and canonical skill identity: `target_role`, `skill_id`,
  `skill_name`, `skill_category`.
- Candidate evidence: `candidate_status`, `verification_status`,
  `candidate_evidence`.
- Market evidence: `market_jobs_with_skill`,
  `market_relevant_jobs_total`, `market_observed_frequency_pct`,
  `market_priority_rank`, `market_evidence_level`,
  `market_evidence_status`.
- ESCO evidence: `esco_mapping_status`, `esco_relationship`,
  `esco_label`.
- Interpretation: `priority_score`, `priority_score_method`,
  `extraction_incomplete`, and `explanation`.

The Phase 3 profile excludes the full extracted CV text. Skill evidence
snippets may still be present in the candidate evidence returned by this
engine; callers should handle those excerpts as personal information.

## 7. Validation and tests

The skill-gap test suite covers:

1. Mentioned skills remain unverified.
2. Explicit verified status is preserved.
3. Missing mentions are not treated as confirmed deficiencies.
4. Incomplete extraction is handled cautiously.
5. Rejected evidence is not counted as demonstrated.
6. Market and ESCO evidence remain traceable.
7. Unsupported roles are rejected.
8. Invalid candidate input is rejected.
9. Output is deterministic and priority-sorted.
10. ESCO importance does not inflate the market-only score.

Phase 3 regression tests should continue to pass alongside the Phase 4
tests so changes to the new engine do not break CV reading, section
extraction, skill normalization, or profile validation.

Controlled synthetic tests validate expected program behavior; they do not
establish real-world CV extraction accuracy or prove that the current job
sample represents the entire market.

## 8. Known limitations and next steps

- Job-market frequencies depend on the current collected UK postings,
  relevant-job filtering, description completeness, and canonical skill
  matching coverage.
- A CV skill mention does not establish proficiency.
- A missing CV mention is ambiguous and may reflect omission or extraction
  failure rather than a genuine skill deficiency.
- ESCO coverage is intentionally limited to explicit exact-label mappings.
- The priority score describes observed market frequency only. It is not
  a candidate score or a complete measure of occupational importance.
- No readiness percentage, learning recommendation, quiz, or proficiency
  verification workflow is implemented by this engine.

These limitations should remain visible when the engine is integrated into
later GradPath phases.
